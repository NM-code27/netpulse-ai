# NetPulse AI -- Predictive Network Observability & Root-Cause Intelligence

A full-stack predictive network-operations platform: live synthetic telemetry
across a 20-branch enterprise network, ML-driven outage-risk forecasting,
anomaly detection, topology-aware root-cause correlation, an LLM troubleshooting
assistant, and business-impact estimation -- all backed by a held-out,
chronologically-split model evaluation, not just a pretty dashboard.

**The standout feature:** inject a fault scenario (WAN link degradation, a
device outage, a DNS failure, an app-tier latency spike) from the dashboard
and watch, in real time: the risk score climb, a predictive-warning alert fire
with an estimated lead time, the root-cause engine rank *why* (WAN link? device?
shared DNS? shared app tier?) using the network's actual topology, and an AI
assistant explain it in plain language with concrete next steps.

## Why this exists

Modeled on the problem Cisco's AgenticOps / ThousandEyes / Splunk observability
stack solves in production: most NOC teams find out about degradation after
users complain. This project asks "can a lean, fully-free stack forecast it
20-30 minutes ahead of time and explain the likely cause?" -- and backs the
answer with an honest, held-out evaluation report instead of just a demo.

## Architecture

```
                     ┌─────────────────────┐
  Browser  ────────▶ │  Next.js dashboard   │  (Vercel)
                     └──────────┬───────────┘
                                │ REST (JSON)
                     ┌──────────▼───────────┐
                     │   FastAPI backend     │  (Render)
                     │  ┌─────────────────┐  │
                     │  │ live simulator  │  │  ticks every 5s
                     │  ├─────────────────┤  │
                     │  │ forecasting +   │  │  XGBoost (regression + classifiers)
                     │  │ anomaly models  │  │  Isolation Forest
                     │  ├─────────────────┤  │
                     │  │ root-cause +    │  │  rule+ML correlation over topology
                     │  │ business impact │  │
                     │  ├─────────────────┤  │
                     │  │ LLM assistant   │  │  Ollama (local) / Groq (hosted, free)
                     │  └─────────────────┘  │
                     └──────────┬───────────┘
                                │
                     ┌──────────▼───────────┐
                     │  Postgres (Neon free) │   -- SQLite locally, zero setup
                     └───────────────────────┘
```

Topology: 1 HQ datacenter + 20 branch offices, each with a WAN uplink, an edge
router, and an access switch, plus two **shared** hub-side services (DNS
resolver, core application tier) that any site's traffic depends on. That
fan-in/fan-out shape is what makes root-cause correlation meaningful: a single
WAN link failing hurts one site; DNS or the app tier failing hurts many sites
at once -- and the correlation engine has to tell those apart from topology
alone. See [backend/app/data/topology_seed.py](backend/app/data/topology_seed.py).

## The ML pipeline

| Capability | How |
|---|---|
| Forecasting | XGBoost regressor per metric family, predicting the value 30 minutes ahead from rolling features |
| Predictive-risk / lead time | XGBoost classifiers at 10/20/30-minute horizons -- "will this breach its threshold in time T?" |
| Anomaly detection | Isolation Forest per metric family, trained only on non-fault periods |
| Root-cause correlation | Rule-based scoring over live anomaly scores across the topology (own WAN link vs. own device vs. shared DNS vs. shared app tier), weighted by how many other sites are affected right now |
| Business impact | Users/apps/sites affected, derived from the documented topology + the root-cause category |

All of it trains against a synthetic but statistically realistic historical
dataset (diurnal load curves, autocorrelated noise, injected fault windows)
generated by [backend/app/simulator/historical.py](backend/app/simulator/historical.py),
with faults deliberately stratified across the train/test time split so the
held-out evaluation actually has fault examples to score against --
see [backend/app/ml/train.py](backend/app/ml/train.py) and the in-app
**Model Evaluation** page for the real numbers (precision/recall/PR-AUC per
horizon, forecast MAE/RMSE, false alarms per entity-day, root-cause top-1/top-3
accuracy -- all computed on data the models never trained on).

## Real-world validation (genuinely real data)

Everything above is synthetic. One page in the dashboard, **Real-World Data**,
is not: it uses [RIPE Atlas](https://atlas.ripe.net), a free public
internet-measurement network RIPE NCC has run continuously since 2010 -- real
ping latency to real DNS root servers, from real distributed probes
worldwide, no account required. For each real series, a fresh model is
trained with the exact same chronological-split methodology as the main
pipeline, directly on that real data, and compared against a naive
"predict no change" baseline -- reported honestly either way (one of the two
measurements currently beats the baseline, one doesn't).

```bash
cd backend
python -m app.realworld.fetch_ripe_atlas   # pulls ~48h of real measurement data
python -m app.realworld.validate            # trains + evaluates against it
```

See [backend/app/realworld/](backend/app/realworld/).

## Running it locally

Needs Python 3.12+, Node 20+. Everything defaults to free/local: SQLite for
the DB, Ollama for the assistant.

```bash
# Backend
cd backend
python -m venv .venv && . .venv/Scripts/activate   # or source .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
python -m app.simulator.historical   # generates ~2M rows of historical telemetry (a few minutes)
python -m app.ml.train               # trains all models, writes the evaluation report
uvicorn app.main:app --reload --port 8000

# Frontend (separate terminal)
cd frontend
npm install
npm run dev
```

Open http://localhost:3000. The live simulator starts ticking immediately on
backend startup; give it ~30-60 seconds for the first scoring pass to populate
risk scores, then use the **Inject a fault scenario** panel on the Overview
page to trigger the demo.

For the assistant: install [Ollama](https://ollama.com), run `ollama pull
llama3.1`, then `ollama serve`. `LLM_PROVIDER=ollama` (the default) will pick
it up automatically. If Ollama isn't running, the assistant falls back to a
deterministic template built from the same evidence -- it never goes blank.

### Running with Docker (closer to production)

```bash
docker compose up --build
```

Spins up Postgres + the backend + the frontend together (see
[docker-compose.yml](docker-compose.yml)).

## Deploying for free

- **Backend** -> [Render](https://render.com) free web service, built from
  [backend/Dockerfile](backend/Dockerfile) (see [render.yaml](render.yaml)).
  Ollama can't run on Render's free plan, so set `LLM_PROVIDER=groq` and a free
  [Groq](https://console.groq.com) API key -- the assistant still works for
  anyone who opens the deployed link.
- **Database** -> [Neon](https://neon.tech) free Postgres tier; set
  `DATABASE_URL` on Render to the connection string it gives you.
- **Frontend** -> [Vercel](https://vercel.com), importing the `frontend/`
  directory as the project root; set `NEXT_PUBLIC_API_URL` to the Render
  backend's URL.

## Honesty notes (read this before quoting the numbers)

- All telemetry is synthetic. It's statistically realistic (diurnal load,
  autocorrelated noise, parameterized fault ramps) but it is not a production
  network capture.
- The evaluation report is computed on a genuinely held-out, chronologically
  later slice of the data the models never trained on -- not a cross-validation
  shuffle, which would leak future information into the past.
- Root-cause accuracy (~71% top-1, ~94% top-3 in the current report) is a
  rule+ML hybrid over a 4-category topology, not a general-purpose classifier --
  it's intentionally scoped to what topology-aware correlation can actually do
  with this fault catalog.
